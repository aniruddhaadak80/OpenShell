OpenShell uses four label groups to show what an issue is, where it stands, what work it needs next, and who is expected to act. The [workflow label manifest](https://github.com/NVIDIA/OpenShell/blob/main/.agents/workflow-labels.json) defines their names, descriptions, and colors.

## Read the Four Axes

| Axis | Meaning | Rule |
| --- | --- | --- |
| `type:*` | Kind of issue: bug, chore, feature, spike, or support. | At most one. It may be absent during intake; classify it from evidence before advancing the work. |
| `state:*` | Current assessment or work state. | Exactly one on an open issue once the intake workflow has run. |
| `needs:*` | The next missing work product or information. | At most one. It may be absent while a human makes a disposition or assignment decision. |
| `ready-for:*` | The actor expected to move the issue forward. | Exactly one on an open issue once intake has run. |

Use `state:new`, `state:validated`, `state:accepted`, `state:in-progress`, and `state:in-review` to describe the issue's current position. `needs:info`, `needs:plan`, `needs:pr`, `needs:spike`, and `needs:rfc` describe the next work. `ready-for:human` includes the contributor who owes information, the triage engineer, a reviewer, or a maintainer making a decision; the issue discussion identifies which person should act.

GitHub's closed status and reason describe completed or declined work. Do not add terminal `state:done` or `state:canceled` labels. When closing a new issue, clear `needs:*` and `ready-for:*` labels that no longer describe a next action. The migration leaves already closed items untouched.

`status:stale` is an inactivity marker outside the four workflow axes. It can appear on an issue or pull request without creating a conflicting `state:*` label. The stale workflow does not close items automatically.

GitHub's built-in issue type is separate metadata. Use `type:*` for the more specific workflow classification. Conventional Commit types describe commits and do not determine issue type. Usage questions may use `type:support`; suspected vulnerabilities belong in the private process in `SECURITY.md`, not a public `type:security` issue.

## Intake and Disposition

Non-maintainer issues start at `state:new` and `ready-for:agent`. That combination makes the issue eligible for initial screening only. For this rollout, a human invokes triage. The triage skill sends findings to `#openshell-triage` for the duty engineer and collaborators to discuss. The engineer directs any public response or label change. Aim to reach an explained acceptance or decline promptly; use `state:validated` with `ready-for:human` only while a genuine maintainer decision is pending.

Maintainer-authored issues bypass triage for this rollout and enter `state:accepted` with `ready-for:human` for scheduling and assignment. The separate automatic-triage follow-on will reconsider that exception. A maintainer still identifies the issue's type and next work when those are not evident from the submission.

Only a human decides whether to accept or decline work, authorizes a spike or RFC, and places an issue on the roadmap. An agent never infers acceptance from technical validity. A maintainer may record acceptance with `state:accepted` or roadmap placement. `needs:rfc` always requires `ready-for:human`; maintainers direct the RFC and assign its number. `needs:spike` represents an approved, bounded investigation, not a promise to implement its findings.

## Authorize Agent Work

`ready-for:agent` is not a general permission to implement. Outside initial screening, a human applies it only after reviewing and authorizing the next phase. An unattended agent must check the full combination of acceptance or roadmap placement, the relevant `needs:*` value, `ready-for:agent`, and any required approved plan. A request for a plan authorizes planning only; an implementation request follows plan approval.

A direct user request authorizes the phase it explicitly names even when the issue's labels are missing or incomplete. The agent names the discrepancy and continues without manufacturing an unattended-queue authorization label. General build agents do not handle `topic:security` issues; specialized security skills preserve the private review and human decision gates.

## Review Common Combinations

| Situation | Labels on the issue | Next action |
| --- | --- | --- |
| New community report | `state:new`, `ready-for:agent`; `type:*` optional pending assessment | Human invokes triage screening. |
| Needs an answer from the reporter | `state:new` or `state:validated`, `needs:info`, `ready-for:human` | Ask a specific question and reassess the answer. |
| Validated, waiting for disposition | `type:bug` or `type:feature`, `state:validated`, `ready-for:human` | Maintainer accepts or declines promptly. |
| Accepted, waiting for a plan | `state:accepted`, `needs:plan`, `ready-for:human` | Human assigns or explicitly queues planning. |
| Approved plan, agent may implement | `state:in-progress`, `needs:pr`, `ready-for:agent` | Authorized agent prepares the PR. |
| Plan or PR ready for review | `state:in-review`, `needs:plan` or `needs:pr`, `ready-for:human` | Human reviews and either approves or requests another pass. |
| Reopened after an earlier close | One current `state:*` and one `ready-for:*`, selected from the work now needed | Reassess the new information and clear obsolete labels before work resumes. |

The following combinations need correction: two labels from one single-valued axis; `state:new` with `needs:pr`; `state:validated` with `ready-for:agent` for implementation; `needs:rfc` with `ready-for:agent`; or `state:in-progress` with no known authorized next work. A missing `type:*` during intake is a classification task, not a reason to guess from the current label backlog. The migration rehearsal reports ambiguous historical combinations for human review.

## Pull Requests

Keep issue workflow labels on the linked issue. A pull request does not need to repeat them. If a pull request has no linked issue, labels from these axes are optional and must not be assumed to represent an accepted issue. Review and merge state remain visible in GitHub's pull request interface.
